Correction to my earlier conclusion: PerfectStorePro did receive and process the callback.

The production log sequence is:

08:51:54  POST /api/perfectstore/stockfix/capture-context → 200
08:52:06  POST /api/perfectstore/stockfix/attribution → 404

So:

The secure iframe launched.
StockFix sent a callback that PerfectStorePro accepted.
PerfectStorePro called its attribution route.
The route returned 404 before calling StockFix’s server-to-server PATCH.
Why Linda’s name did not pull through
PerfectStorePro deliberately verifies that the captured task ID exists in its own authorized StockFix task cache before assigning a rep.

For this capture, the callback task ID was not found in that cache, so PerfectStorePro safely stopped with:

StockFix task not found

That is why Linda was not assigned. It is not an iframe link problem, origin-validation problem, callback-delivery problem, or API-key problem.

What needs fixing
The new StockFix task-only fallback is loading tasks from nexus_tasks, but the task ID being captured is not available in the StockFix task data that PerfectStorePro uses to validate attribution.

The two task sources must be aligned:

Option 1 — StockFix: Ensure fallback tasks from nexus_tasks are also exposed through the task feed that PerfectStorePro caches.
Option 2 — PerfectStorePro: When attributing a callback, securely retrieve the exact task from StockFix server-to-server, then verify its exact store, P&G client, and signed rep scope before assigning it.
PerfectStorePro must not simply trust unknown callback IDs, because that would weaken the security controls.
